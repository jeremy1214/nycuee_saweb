# 網站內容後台、雙登入與權限管理計畫

> 階段進度：已加入帳密登入、管理員 Session、受保護後台首頁、`admin/admin` 初始化指令，以及 Docker Compose／Caddy 設定；依要求未執行驗證。Google 登入、帳號管理介面及內容管理仍待後續實作。啟動方式見根目錄 README。下列「目前狀況」保留原始規劃時的架構背景。

## 1. 架構判斷與需要調整的地方

**建議保留現有 React 前台，新增自架後端、資料庫與管理介面，不必重寫整個網站。**

依已確認的方向，採用 Linux＋Docker，支援 Google 與使用者名稱／密碼登入；編輯者依授權範圍修改內容，由管理員審核發布。第一版涵蓋整個活動區與圖片。

目前專案是 React 19＋Vite＋TypeScript，使用 Hash Router；`backend` 尚無實作。主要限制如下：

| 項目 | 目前狀況 | 要做的改動 |
|---|---|---|
| 活動、分類、其他活動介紹 | JSON 在建置時載入 | 改由 API 讀取已發布資料 |
| 系隊、系學會、學習資源 | 已有結構化 JSON | 保留現有頁面，後續逐一接入後台 |
| 首頁輪播、行事曆、聯絡資訊 | 部分資料寫在 TypeScript | 後續拆出可管理的內容模型 |
| 首頁近期活動 | 已共用活動資料 | 第一版一起改接 API |
| 圖片 | 放在前端 `public` 目錄 | 新增上傳、檔案驗證、引用與儲存管理 |
| 登入、權限、審核、紀錄 | 尚未實作 | 新增伺服器端身分驗證與授權 |
| 資料驗證 | 活動與資源較完整，其他模組不一致 | 抽出共用規則，寫入與發布時由後端驗證 |

關鍵依據是[活動資料載入程式](../frontend/src/features/activities/data/activityRepository.ts)：目前使用 `import.meta.glob` 將 JSON 載入網站。單純新增編輯表單，無法讓正式網站永久保存更新。

目前「無法透過一般內容後台維護」的項目，需要區分：

- **現有架構未提供的能力**：線上儲存、上傳、帳號管理、審核、版本還原，需要新增後端才能做到。
- **仍屬程式開發的項目**：版型、CSS、互動行為、新種類的內容區塊，第一版仍由工程師修改；後台管理既有版型中的文字、圖片、排序與分頁。
- **外部系統資料**：本後台不能直接修改校方網站、社群平台或已匯入個人 Google 日曆的活動。
- **尚未納入第一版的內容**：首頁行事曆目前使用獨立示意資料，[行事曆元件](../frontend/src/features/home/components/EventCalendar.tsx) 的日期也固定為 2026-10-10，必須另行改造才能同步。

## 2. 目標架構與管理流程

### 技術組合

預設採用以下組合，延續現有 TypeScript 技術：

| 層級 | 選擇與用途 |
|---|---|
| 公開網站 | 保留 React、Vite、既有網址與視覺 |
| 管理介面 | 同一前端專案新增 `/#/admin`，使用獨立後台版面並延遲載入 |
| 後端 | NestJS＋TypeScript，集中處理驗證、授權、審核與資料存取 |
| 資料庫 | PostgreSQL＋Prisma migrations |
| 圖片 | 後端管理的持久化磁碟目錄，透過媒體 API 提供 |
| 部署 | Docker Compose＋Caddy，以同一網域提供前台與 `/api`，啟用 HTTPS |

圖片不存進容器的暫存檔案系統；資料庫與媒體都需要持久化及異機備份。

### 登入與權限

Google 與帳密登入共用同一個內部使用者身分，避免同一人有兩套權限。

- 不開放公開註冊。管理員建立帳號、指定編輯範圍、停用帳號。
- Google 登入採授權名單，使用 Google 的 `sub` 識別帳號。已有帳密的使用者須登入後主動綁定 Google，不只因 email 相同就自動合併。[Google 身分識別文件](https://developers.google.com/identity/openid-connect/reference)
- 本機密碼使用 Argon2id 雜湊；第一版由管理員產生短效、單次使用的啟用／重設連結，透過既有聯絡方式交付，使用者自行設定密碼。[OWASP 密碼儲存指引](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
- 兩種登入都建立伺服器端 Session，使用 Secure、HttpOnly Cookie，加入 CSRF 防護與登入限速。停用帳號或變更權限後，下一次請求即依新權限判斷。[Session 指引](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)、[CSRF 指引](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)

第一版角色：

| 角色 | 能做的事 |
|---|---|
| 訪客 | 閱讀已發布內容 |
| 編輯者 | 編輯被授權分類或指定活動、上傳圖片、預覽與送審 |
| 管理員 | 管理全站內容、發布／退回／下架、管理帳號與授權、查閱操作紀錄 |

權限由後端逐筆檢查，包含圖片存取與草稿預覽，不能只靠前台隱藏按鈕。分類設定與精選活動入口由管理員管理。

### 編輯與發布流程

**建立草稿 → 編輯與預覽 → 送審 → 管理員發布或退回。**

- 已發布內容保留公開版本；編輯新草稿時，訪客繼續看到原版本。
- 送審版本凍結；要修改須撤回或退回草稿，避免管理員審到不同內容。
- 發布時一起驗證分類、圖片與分頁引用，成功後才切換公開版本。
- 下架保留歷史資料；第一版不提供內容永久刪除。
- 還原歷史版本會產生新草稿，再經發布流程。
- 同時編輯透過版本號檢查，衝突時提示重新載入，不能默默覆寫。

## 3. 第一版介面與資料介面

後台提供六個主要頁面：

1. **待辦總覽**：自己的草稿、待審項目、退回原因。
2. **活動管理**：搜尋、篩選、建立、編輯、送審與下架。
3. **活動編輯器**：基本資料、介紹、圖片、章節、分頁與排序。
4. **其他活動介紹**：管理現有常態介紹、相簿與組別內容。
5. **媒體管理**：上傳、預覽、選圖、查看引用位置。
6. **帳號與紀錄**：管理員管理授權及檢視變更紀錄。

第一版使用結構化表單，沿用現有活動版型，保留「共用簡介／獨立介紹分頁」、雙主圖與可省略章節圖片等行為。預覽重用前台顯示元件，避免後台預覽和正式頁長得不同。

資料與 API 的分工：

- 資料庫保存使用者、登入身分、Session、授權、活動、分類、其他活動介紹、版本、媒體與操作紀錄。
- 日期、分類、識別值等可查詢欄位獨立保存；巢狀章節與分頁使用經驗證的 JSONB。
- 保留既有活動識別值與網址，發布後不允許直接改動識別值。
- 公開 API 使用 `/api/v1/public/*`，只回傳已發布版本。
- 後台 API 使用 `/api/v1/admin/*`，提供草稿編輯、送審、退回、發布、下架、版本與媒體操作。
- 驗證失敗回傳欄位錯誤；未登入、無權限與編輯衝突分別使用 401、403、409。
- 用 OpenAPI 與共用資料驗證規格固定介面，讓前後端可以各自開發。

圖片第一版接受 JPEG、PNG、WebP，單檔上限預設 10 MB；由後端確認實際格式並重新編碼、限制尺寸。草稿圖片必須經授權存取，發布後才提供公開版本；曾公開的圖片無法保證從訪客已下載的副本中撤回。

前台須補齊載入中、空資料、錯誤與重試狀態；活動發布後，下次讀取即可取得新資料，不需重新部署。分類導覽與首頁近期活動也使用同一份公開資料。

## 4. 分階段與共同實作項目

### 階段一：固定規格與建立基礎

完成內容模型、權限矩陣、API 契約、測試資料及 Docker 開發環境，先讓多人開發有一致依據。

### 階段二：完成活動後台的完整流程

依契約並行實作登入、內容服務、圖片服務與後台表單，整合出「登入 → 編輯 → 上傳 → 送審 → 發布 → 前台顯示」的完整流程。

### 階段三：匯入舊資料、驗收與上線

匯入活動 JSON、分類、其他活動介紹及圖片，驗證既有網址與內容完整性，再切換正式資料來源。

### 階段四：擴充全站內容管理

依序接入首頁輪播與行事曆、系隊與系學會、學習資源與聯絡資訊，沿用同一套帳號、版本與發布機制。行事曆屆時改用真實台灣日期，支援同日多筆活動，並讓活動、日曆與 ICS 共用日期型活動來源。

### 分工表

| 項目 | 交付內容 | 相依關係 |
|---|---|---|
| A：規格與契約 | 資料模型、權限矩陣、OpenAPI、共用驗證規則 | 最先完成 |
| B：後端與部署基礎 | NestJS、資料庫 migrations、Docker、健康檢查 | 依 A |
| C：登入與帳號權限 | 雙登入、綁定、Session、帳號管理、授權檢查 | 依 A、B |
| D：內容與發布服務 | 草稿、送審、發布、歷史版本、衝突檢查 | 依 A、B，整合 C |
| E：媒體服務 | 上傳、驗證、草稿保護、公開存取、引用檢查 | 依 A、B，整合 C |
| F：後台介面 | 編輯表單、媒體選擇、預覽、審核及帳號頁 | A 完成後可用 mock API 並行 |
| G：前台與資料遷移 | 非同步讀取、首頁與導覽連動、舊資料匯入 | A 完成後可先開發，整合 D、E |
| H：整合驗收與維運 | 權限測試、部署、備份還原、交接文件 | 早期準備，最後整合驗收 |

**建議分成四條工作線：平台與登入、內容與媒體、後台介面、前台與遷移。** 每條工作線各自負責模組；共用型別與契約由 A 的負責人統一維護，避免多人同時改出不同格式。

## 5. 驗收、上線與預設邊界

### 第一版驗收條件

- [ ] Google 與帳密登入均可使用；綁定、登出、重設及停用流程正常。
- [ ] 編輯者即使直接呼叫 API，也無法修改未授權內容、發布或變更自身角色。
- [ ] 草稿文字與未發布圖片不會透過公開 API 外洩。
- [ ] 修改已發布活動，不影響線上內容；發布後前台與首頁近期活動一致更新。
- [ ] 雙人編輯、審核期間修改、重複發布不會造成資料被覆寫或錯誤版本上線。
- [ ] 電機營、電機週、其他活動介紹的既有網址、分頁與圖片顯示維持正常。
- [ ] 下架分類精選活動時，必須同時更新入口或阻擋操作，避免導覽連到不存在的公開頁。
- [ ] 非法圖片、過大檔案與刪除仍被引用的圖片均被拒絕。
- [ ] 通過既有測試、建置，以及新增的後端整合與瀏覽器流程測試。

### 遷移與上線

上線採測試環境先行：完成可重跑的匯入工具、逐筆比對與備份還原演練，再短暫凍結舊 JSON 更新並切換。切換後活動資料庫成為唯一正式資料來源，JSON 保留作遷移基準。

預設備份為每日資料庫與媒體異機備份、保留 30 天；建立服務故障、備份失敗與磁碟空間告警。正式上線前需要準備網域、Linux 主機、Google OAuth 設定、異機備份位置及首位管理員。

### 預設邊界

第一版不包含自由拖拉版型、公開會員註冊、校務 SSO、Google 日曆雙向同步或聯絡表單收件後台。後續模組沿用本次基礎擴充，不另建第二套登入與權限系統。
